<problem>
ggml's scheduler can "offload" a large-batch MUL_MAT whose weight (src0) lives in a host buffer to a GPU backend (ggml_backend_sched, ggml/src/ggml-backend.cpp around line 1153: `if (sched->op_offload && src_backend_id == sched->n_backends - 1 && ggml_backend_buffer_is_host(src->buffer))`). In this fork that condition never fires, because a BLAS (Accelerate) backend is registered last, so host weights map to BLAS and src_backend_id is not the last backend. The fix is known — replace that condition with:

    // tosh: "the last backend" is the CPU only without an accelerator; with BLAS (Accelerate)
    // registered the host weights map to BLAS and no op was ever offloaded. Any host-side
    // backend (CPU or ACCEL) holding the weight qualifies.
    const enum ggml_backend_dev_type src_type = ggml_backend_dev_type(ggml_backend_get_device(sched->backends[src_backend_id]));
    const bool src_on_host = src_type == GGML_BACKEND_DEVICE_TYPE_CPU || src_type == GGML_BACKEND_DEVICE_TYPE_ACCEL;
    if (sched->op_offload && src_on_host && ggml_backend_buffer_is_host(src->buffer)) {

Apply that fix first. With it, a model at `-ngl 0` computes every prompt-batch MUL_MAT (batch >= the Metal backend's op_offload_min_batch_size; see ggml_backend_metal_device_offload_op in ggml/src/ggml-metal/ggml-metal.cpp) on the card from a scheduler copy of the host weight. The result is GARBAGE on every model tried: Qwen3-0.6B Q8_0 answers "@@@@@@@@..." on a 570-token prompt; Qwen3-4B Q4_K_M and gemma4 12B Q8_0 are garbage too. Suspects (unproven): the scheduler's copy of a weight into a Metal buffer (how the split input copy is made — ggml_backend_tensor_copy / cpy_tensor_async / set_tensor into a private buffer, and whether the compute is ordered after the copy completes); alignment/padding of that copy versus what the fork's GCN kernels assume (the fork's "aligned mat-vec reads" for gfx600, env TOSH_MV_ALIGN=0/1, and the wave64 mul_mm path); a quantized-type layout difference; a missing synchronisation.
